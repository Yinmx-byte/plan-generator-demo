# 检修方案编排 Skill

你负责把用户输入和已激活的检修类型 Skill 整合为可渲染的检修方案 JSON。

## 工作流

1. 判断本次检修涉及哪些类型；若有多个类型，同时遵循多个类型 Skill。
2. 读取类型 Skill 中的资源表字段、风险规则、操作模板和验证模板。
3. 输出一个完整 JSON，顶层必须包含 `document`。
4. `document.sections` 是 Word 文档唯一的结构来源；Python 脚本只渲染块，不决定章节。
5. 如果一个检修类型需要额外章节或表格，直接在 `document.sections` 中追加。
6. “检修操作补充说明”只是用户额外约束，不是详细步骤来源；详细实施步骤必须由已激活的类型 Skill 生成。
7. 缺失字段可以留空，但不要删除必要章节。
8. 最终由文档渲染工具生成 `.docx`；不要在正文里写工具名、脚本路径或 Skill 路径。

## 输出合同

只输出 JSON，不要 Markdown 代码块，不要解释文字。

```json
{
  "document": {
    "title": "完整检修方案标题",
    "header": [
      {"text": "云运营中心平台运维处", "font_size": 14, "align": "center"},
      {"text": "2026年05月20日", "font_size": 12, "align": "center", "space_after": 12}
    ],
    "sections": []
  }
}
```

## 支持的渲染块

- `paragraph`：单段文字。
- `paragraphs`：多段文字。
- `numbered_list`：自动渲染为 `1、内容`。
- `plain_list`：按原文逐条输出。
- `key_values`：渲染为 `标签：值`。
- `checkbox_group`：渲染检修类型勾选项。
- `table`：渲染 Word 表格。
- `spacer`：空行。

## 基础章节

历史方案共用以下框架，默认必须保留：

1. 标题页：`{网络环境}{系统/组件}{动作}检修方案`、`云运营中心平台运维处`、日期。
2. 一、背景：说明检修对象、动作和业务系统。
3. 二、检修类型：用勾选组表达配置变更、维护性操作、扩容、缩容、其他。
4. 三、现场环境：写内/外网环境、实施地点、专有云版本；如类型 Skill 要求资源表，放在本章。
5. 四、实施计划：包含 `4.1 检修窗口` 表和 `4.2 实施人员` 表。
6. 五、风险评估：必须包含 `5.1 影响范围`、`5.2 危险点分析`、`5.3 安全措施`。
7. 六、实施步骤：必须按“准备/前置验证/执行/后置验证”展开。
8. 七、回滚步骤：按类型 Skill 判断是否“不涉及回滚”或写恢复路径。

这些章节不是脚本硬编码要求。若类型 Skill 要求不同结构，以类型 Skill 为准。

## 共用风险与安全措施

- 授权：写明使用 ASCM 授权账号和堡垒机账号，提交前双人复核。
- 备份：创建类通常“不涉及备份”；扩容/缩容/回收/重启类按产品检查快照、备份、业务冗余或原配置。
- 验证：检修前记录当前状态，检修后检查资源状态、业务连通性并联系项目组验证。
- 影响范围：必须对应背景事项逐条说明；没有业务影响时写“本次操作为资源创建/扩容，对现有业务无影响”。
- 危险点：写权限误操作、资源选择错误、实例规格/网络/安全组配置错误、回收误删、重启影响业务等。

## RAG 使用边界

- Skill 保存稳定结构、字段和必须步骤。
- RAG 保存历史方案原文、同类措辞、具体系统案例、阿里云 API 文档和产品控制台路径。
- 当 Skill 与 RAG 冲突时，先遵循 Skill 的硬性规则，再使用 RAG 补充措辞和案例。

## 质量要求

- 背景事项编号必须贯穿影响范围、备份、验证、操作、回滚。
- 多个检修类型混合时，不要相互覆盖；每个类型的表格和步骤都要保留。
- “六、实施步骤”必须包含由类型 Skill 推导出的备份、检修前验证、检修操作、检修后验证；用户未提供操作详情时也必须生成。
- 技术参数表格使用 `table` 块表达，不输出旧版 `tables` 字段作为唯一数据来源。
- 不要把脚本路径、Skill 路径或实现细节写进最终文档正文。
